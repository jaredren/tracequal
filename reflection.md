# MP2 Reflection

## What did you build

TraceQual is a disclosure scaffold for qualitative researchers whose analysis involves AI. It reads a researcher-AI chat transcript and produces a structured matrix documenting each analytic decision the researcher made about an AI suggestion, intended to be inspectable in an appendix. It is not a tool for AI coding; it makes existing AI involvement legible to reviewers. The locked v1 build includes a JSON schema for the decision matrix (`schema/decision_matrix_v1.json` with rationale in `docs/schema_notes.md`), a versioned extraction prompt (`prompts/extract_decisions.md`), a Python validation harness (`scripts/validate_extraction.py`), cached extractions under `outputs/` (prompt v1.0.0 re-locked after v1.1.0 regression), and build documentation of what the single-fixture validation run showed.

## What decisions did you make

I built in Cursor with Python rather than a notebook-only script because extraction, parsing, and validation needed to stay testable outside the deliverable notebook. The most consequential schema decision was replacing model self-reported confidence with rule-derived confidence from `decision_stated` and `reasoning_stated` booleans (`tracequal/extractor.py`, `derive_confidence`), making the signal inspectable rather than opaque. I preserved the unsuccessful prompt v1.1.0 revision and its cache rather than deleting it, so the regression from 12 to 10 harness PASS checks remains auditable in `prompts/prompt_changelog.md`. I bounded format support honestly: Claude export JSON is tested; ChatGPT tree exports are documented as unsupported. Relative to my MP2a declaration, the audience framing shifted from "researchers who use LLMs mid-analysis" toward a broader disclosure framing for any qualitative workflow where AI suggestions enter the analytic record.

## What would you do differently

Two tool-level changes stand out. First, I would add a `transcript_span` field to each decision row, holding a verbatim excerpt or line range from the participant transcript the suggestion concerned. The synthetic fixture codes "lines 12-19" repeatedly, but the matrix stores only turn-level summaries; a reader cannot verify a row against primary data without returning to the full chat. That field would require a schema bump, prompt instruction, and harness fixtures asserting span presence on coding rows. Second, I would make the cache path version-aware from the first extraction run. The version-provenance bug surfaced when `outputs/synthetic_long_decisions.json` diverged from prompt-versioned caches; `default_cache_path()` now encodes the prompt version, but retrofitting that after unversioned runs cost reconciliation work I would avoid upfront.

## What does this work demonstrate

The schema design connects decision granularity to methods literature: `analytic_stage` enums follow Braun and Clarke's phases (Feuston and Brubaker 2021 motivate stage-specific disclosure), and the matrix avoids IRR-style reporting in favor of an audit trail (McDonald et al. 2019) [competency: Reflective methodology]. The validation harness implements a four-state outcome model (PASS, FAIL, PENDING, N/A) with a sample-size guard on confidence calibration (`MIN_CALIBRATION_SAMPLE = 5`), treating descriptive confidence stats as N/A when buckets are too small [competency: Validation and evaluation]. Reflexivity shows in preserving the failed v1.1.0 prompt and documenting confidence medium-collapse under the v1.1 rule as an empirical finding in `docs/schema_notes.md`, not hiding it as a bug [competency: Documentation and reproducibility]. The end-to-end Python pipeline demonstrates computational support for HCD methods work without substituting for analytic judgment [competency: Computational tools for HCD work].
